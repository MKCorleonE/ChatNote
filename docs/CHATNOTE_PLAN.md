## 1. 产品方向

项目正式名称为 **ChatNote**。产品目标是独立的跨平台 AI 对话与笔记软件，面向 iPadOS、macOS、iOS、Windows、Android。

第一阶段以学习复杂知识为核心场景：沿主线理解内容，在某个词语、公式或段落上建立可持续追问的批注，最后把对话整理为可复习、可导出的笔记。后续可以扩展到阅读、研究和写作。

核心体验：**对话 → 选中原文 → 批注追问 → 继续深入 → 回到主线 → 整理笔记**。

产品界面、对话数据、批注关系和版本规则由 ChatNote 自己管理。模型服务作为可以替换的能力接入。以前提交的功能请求保留为项目历史；开发不以官方采纳为前提。

已确定：新名称、独立产品、五个平台目标、沿用现有原型、Windows 先跑通、预留全部平台；界面简洁且有设计感，聚焦当前对话和右侧追问。

已知参考软件：Dendraft，安装于 `C:\Users\Hyper-Boy\AppData\Local\Programs\Dendraft`。安装目录包含 Electron 许可证、Chromium 资源和 `resources/app.asar`，据此判断采用 Electron 打包；尚未确认其界面框架、认证实现和上下文压缩策略。

待确定：历史列表的具体收起交互、开源与商业发布方式、设备可用性、同步与账号方案，以及其他功能优先级。以下新增范围与实现方式是建议。

### 界面设计基线

- 当前对话是视觉中心；右侧按需显示批注对话或追问树。普通对话时可以关闭右侧面板。
- 历史会话入口保持容易找到，但降低持续占用的空间。候选方案为默认收起的窄栏/按钮，点击打开历史抽屉，选中会话后收回；保留固定展开选项。具体形式通过原型比较再确定。
- 延续原型的深色、文字阅读和局部高亮方向，使用留白、字体层级、克制的强调色与轻量动效形成设计感。
- 追问树服务于定位与复习，作为可切换视图；初版不增加常驻全屏节点画布。
- 返回父节点、切换批注、切换会话、进入/退出追问树，应恢复此前阅读位置、展开状态和未发送草稿。

### 从 Dendraft 使用反馈转为 ChatNote 要求

以下问题来自用户使用反馈，尚未独立复现 Dendraft 行为。

| 反馈 | ChatNote 设计要求 |
| --- | --- |
| 分支后长上下文是否压缩不明确 | 完整记录与发送给模型的上下文分开；可按需查看使用了哪些来源、是否摘要以及范围 |
| 回退节点不能停在历史位置 | 按会话/批注/视图保存阅读位置；返回恢复原位置，跳到来源作为独立操作 |
| 切换概览明显卡顿 | 追问树按需加载、局部更新；长列表按需要做虚拟化，建立长会话基准 |
| 希望支持更多模型厂商 | 首版建立通用服务商接口，随后优先增加第二家真实服务商；按厂商验证功能 |
| 过于注重可视化和分支 | 默认以聊天与阅读为主，分支作为追问细节；图形画布暂不进入初版 |

## 2. 现有原型能复用什么

基于 `prototype/index.html`、`app.js`、`app.css`、`core.js` 的当前实现：

| 项目 | 当前情况 | 正式版工作 |
| --- | --- | --- |
| 深色桌面界面 | 主线、侧边批注和导航已有 | 延续布局与视觉，拆成可维护组件 |
| 原文批注 | 单段落选区、重叠高亮和原文定位已有 | 支持真实生成内容、版本与复杂排版 |
| 多轮旁支和子批注 | 数据关系及交互已有 | 接入模型，控制各分支上下文 |
| 追问树 | 父子关系、折叠与定位已有 | 支持多会话、长树与搜索 |
| 本地保存 | 浏览器 localStorage | 迁移到正式数据库，加入备份和迁移规则 |
| 导出笔记 | Markdown 预览与导出入口已有 | 增加结构化备份与恢复，验证安装版文件保存 |
| 模型回答 | 全部预设内容 | 增加真实请求、流式输出、停止、失败恢复 |
| 应用交付 | 网页和 Edge 应用窗口原型 | 生成可安装、升级和卸载的应用 |

现有代码没有 React、Tauri 或正式数据库。这些是下一步新增的工程能力，不能把现有演示当成已经完成的产品。

## 3. 初版范围：v0.1

目标是可日常使用的 Windows 本地版，并为其他平台保留同一套核心数据与业务逻辑。

1. **真实聊天**：新建、切换和重命名会话；流式显示回答；停止生成；失败后可重试。
2. **原文批注追问**：选择助手回答中的文字，创建旁支；高亮可重新打开；旁支可多轮问答。
3. **递归批注**：旁支回答中可建立子批注，并返回父批注或原文。
4. **上下文隔离**：旁支只获得必要主线背景、引用原文、祖先分支背景与自身历史；其他旁支不自动加入。用户明确选择后才把结论带回主线。
5. **追问树**：按真实的父子关系展示记录，支持折叠和定位。
6. **内容呈现**：Markdown、基本公式和代码块可读；首版至少保证普通文本单段落批注可靠，其他选区按验证结果逐项开放。
7. **笔记与数据**：本地持久保存、Markdown 导出、完整结构备份和恢复；重启可复原。
8. **模型设置**：先接入 OpenAI Responses API；API Key 通路与 ChatGPT 套餐通路分别验证；显示实际可用模型与请求错误。
9. **基础设置**：主题、字体、批注开关、模型连接；初版默认沿用原型英文界面，中文界面列入后续优先级讨论。
10. **应用交付**：Windows 安装、启动、升级和卸载验证。聊天数据库与安装目录分离。
11. **阅读连续性**：会话与批注切换后恢复历史位置和草稿；长会话进入追问树可响应，不因切换全量重建所有消息。

初版暂缓：云同步、多人协作、知识图谱、手写、语音、复杂文档阅读、插件市场、自动执行电脑操作和收费体系。它们进入功能清单，后续可调整优先级。

## 4. 技术路线建议

**建议先验证：TypeScript + React + Tauri 2 + Rust + SQLite。**

| 部分 | 技术 | 对用户的意义 |
| --- | --- | --- |
| 界面及大部分产品逻辑 | TypeScript、React、HTML/CSS | 延续网页原型，便于维护复杂聊天与批注界面 |
| 应用外壳与系统能力 | Tauri 2、Rust | 提供安装程序、文件保存、数据库和系统集成 |
| 本地记录 | SQLite | 聊天、批注和笔记保存在设备上，可迁移和备份 |
| 凭据存储 | 各平台安全存储，通过适配层调用 | API Key 和登录令牌与聊天记录分开保护 |
| 模型通信 | 服务商适配层，原生层发起请求 | 统一输出事件与取消操作，按认证方式支持不同能力 |
| 平台专属功能 | 必要时 Swift/Kotlin 或插件 | 处理登录回调、分享、手写等系统功能 |
| 未来同步服务 | 另行选择；TypeScript 服务端是候选 | 需要同步、账号或统一计费时再引入 |

Tauri 官方提供桌面和移动目标，并允许复用 HTML/CSS/JavaScript 界面。这意味着可以共享代码，不代表所有插件、文字选择和系统操作无需适配。[Tauri 介绍](https://v2.tauri.app/start/)、[构建前提](https://v2.tauri.app/start/prerequisites/)

### 其他路线为什么仍要比较

| 路线 | 优点 | 对 ChatNote 的取舍 |
| --- | --- | --- |
| Tauri 2 + React/TypeScript | 可延续原型的网页布局与文本交互；覆盖桌面和移动目标 | 首选验证；移动选区、登录回调、插件和 WebView 差异需要实测 |
| Flutter + Dart | 官方支持 Windows、macOS、Android、iOS；可共享界面与逻辑 | 有竞争力的备选；现有 HTML/CSS 界面需重做，复杂文本批注需重新实现 |
| Electron + React/TypeScript | 桌面生态和打包工具齐全；官方 ChatGPT 登录示例使用 Electron | 桌面备选；移动端还要另选外壳或客户端，应用包通常包含运行时 |
| 各平台原生开发 | 平台交互与系统能力掌控更直接 | 需要维护多套界面；现阶段开发成本较高，保留给有明确必要性的模块 |

平台能力参考：[Flutter 支持平台](https://docs.flutter.dev/reference/supported-platforms)、[Electron 打包](https://www.electronjs.org/docs/latest/tutorial/application-distribution)。上表选型判断是基于 ChatNote 现有原型和场景的工程建议。

Python 可以用于开发辅助、数据处理或未来独立服务；当前建议的客户端主要语言是 TypeScript 和 Rust。无需一开始就学习五个平台各自的全部语言。

## 5. 模型接入与套餐登录

截至 2026-10-08 的官方文档，**Sign in with ChatGPT** 支持在符合条件的应用中授权使用 ChatGPT 套餐。登录身份与套餐使用是不同权限。[官方快速入门](https://developers.openai.com/siwc/quickstart)

- 开源和本地运行应用存在官方接入路线；部分私有客户端也可参与。
- 收费或远程托管产品需要进一步确认适用方式，官方文档提供意向申请入口。
- 合资格 Plus/Pro 用户的请求消耗现有套餐额度，不是新增无限额度。
- 登录并不会让 ChatNote 自动取得用户已有 ChatGPT 聊天或记忆。

参考：[开源与本地应用指南](https://developers.openai.com/siwc/token-sharing-open-source)、[用户套餐使用说明](https://learn.chatgpt.com/docs/sign-in-with-chatgpt)。朋友的软件可能使用这条路线，但在知道软件名称和实现前无法确认。

计划保留两条独立通路：

| 通路 | 初期工作 | 发布条件 |
| --- | --- | --- |
| 用户自己的 OpenAI API Key | 验证普通文本的真实聊天、流式输出和停止 | 按 API 通路实际权限与计费提供功能 |
| Continue with ChatGPT | 验证注册、浏览器授权、回调、令牌刷新、请求和退出 | 确认 ChatNote 发布形式适用，并完成相应平台实测 |

套餐通路当前预览有独立约束：HTTP 需要 `store: false`、`stream: true`，历史由客户端发送；图像生成、托管文件搜索、Code Interpreter、音视频输入和转写等能力不在该通路支持范围。能力清单必须按通路区分，不能假设与 API Key 完全一致。[预览限制](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

普通学习聊天建议直接对接 Responses API；Codex app-server 留作未来编程或工具执行场景的候选。初版不必把整套编程代理运行层带进移动端。

模型名称从实际接入能力中读取；成功完成请求才能验证访问，界面出现模型名称并不代表账号有权限。供应商密钥、用户密钥和 OAuth 令牌不写入公开代码、普通日志、笔记导出或聊天数据库。

ChatNote 自己的同步账号与 OpenAI 连接分开设计。前者负责设备与数据，后者负责调用模型。

## 6. 数据与批注规则

规划实体：Workspace / Session、Conversation、Message、MessageRevision、Annotation、ContextSnapshot、Note、ProviderConnection。

- 主线和每条旁支有独立 Conversation；子批注必须指向实际父旁支中的源消息版本。
- 锚点记录消息 ID、版本 ID、原始文本位置、引用和前后文，不能只保存网页坐标。
- 普通选区先沿用 JavaScript UTF-16 位置定义，并在跨语言数据层明确同一单位；测试中文、emoji、组合字符与重复段落。
- Markdown、公式和代码的显示层需要映射回原始文本，不能直接把渲染后的 DOM 偏移当作正文偏移。
- 生成过程与最终完成版本区分；v0.1 默认在完成的回答上建立批注，停止的部分回答需明确状态后才能成为稳定来源。
- 重新生成新建回答版本，旧批注仍绑定旧版本；匹配不唯一时显示待重新关联，不静默绑定其他文字。
- 保存旁支创建时的上下文快照或稳定来源引用；长对话摘要保留来源范围，并控制输入长度与开销。
- 完整历史在本地保留；模型请求不必每次重复全部历史。短对话在输入预算内保留必要完整上下文，较长对话使用祖先/主线摘要、近期轮次、精确原文引用和当前问题；阈值依据实际模型输入预算定义。
- 对摘要保留版本和来源范围，可查看原文；原文引用与用户明确指定的约束优先保留。超出预算时明确提示或重构上下文，不能任意截断仍假装全部历史可用。
- 来源与上下文详情默认藏在轻量入口中，用户需要时查看，避免让普通聊天充满技术参数。
- 阅读位置优先用可见消息 ID 与局部偏移记录，附带视图状态；加载、展开和布局恢复后再定位，单独保存绝对像素不足以应对排版变化。
- “带回主线”记录来源和摘要，避免重复插入，用户可以预览并编辑。
- 本地保存使用事务及 schema 版本。损坏或无法迁移时保留原文件并提供恢复路径，不能静默用示例覆盖正式记录。
- 先实现备份恢复，再实施数据库迁移；导出包带格式版本，并校验父子关系与引用。
- 原型浏览器存储按用户明确触发的导出/导入迁移到正式版。名称变更不应改动现有存储键而丢失原型记录。

## 7. 跨平台体验与交付

| 平台 | 交互计划 | 安装/发布计划 |
| --- | --- | --- |
| Windows | 沿用主线与右侧批注，键盘、鼠标选区 | exe 安装包或 msi；先验证本地安装 |
| macOS | 共用桌面布局，适配快捷键与窗口 | app/dmg；签名、公证与更新后续逐项验证 |
| iPadOS | 横屏双栏，窄屏可收起批注；触摸、键盘与分屏 | iPad 布局和设备测试；TestFlight 后再考虑正式商店发布 |
| iOS | 主线与批注分页/抽屉切换，保留返回原文路径 | 独立验证小屏、选区菜单、软键盘和生命周期 |
| Android | 手机和平板适配，系统返回、选区与键盘 | 开发 APK；商店发布时另验证对应要求 |

开发顺序建议：Windows 日常可用 → macOS 与 Android 验证 → iPadOS/iOS 验证；如果 iPad 是主要使用设备，可以优先推进 iPad 适配。技术验证阶段就检查移动交互，避免到最后才发现无法复用。

iOS/iPadOS 的 Tauri 构建需要 macOS 与 Xcode；可以使用自己的 Mac 或适合的 macOS 构建环境，Windows 机器不能独立完成这一步。Apple 目标的验收必须有对应环境与设备，未完成时明确标为待验证。[官方构建前提](https://v2.tauri.app/start/prerequisites/)

跨平台应用与跨设备同步是两件事。初期每台设备可以独立保存；后续同步需处理离线编辑、冲突、删除传播、附件、凭据与加密边界。

## 8. 实施阶段与验收

| 阶段 | 工作 | 可检查的成果与通过条件 |
| --- | --- | --- |
| P0 规划基线 | 名称、原型盘点、初版范围、功能清单、技术建议 | 当前计划与功能清单完成；明确确定项和建议项 |

| P2 核心工程 | 数据模型、迁移、组件拆分、Markdown、服务商与存储适配层 | 主线/旁支共享业务模块，平台能力通过接口调用；现有核心行为回归通过 |
| P3 v0.1 | 真实聊天、递归批注、追问树、多会话、导出与恢复 | 完成下方端到端验收；不再依赖预设答案完成用户流程 |
| P4 Windows 内测 | 安装、升级、卸载、性能、错误恢复和长对话 | 可提供朋友试用的安装包；升级保留数据，凭据不进入导出 |
| P5 五个平台 | 平台环境、触屏布局、登录、生命周期、打包 | 每个平台单独记录已验证的系统/设备和功能；未测项不标完成 |
| P6 同步与扩展 | 从功能清单选择同步、文档或复习能力 | 单独定义范围与验收，处理数据冲突和真实使用反馈 |

阶段按完成条件推进；日期和工期在 P1 确认开发环境、接入方式与可用设备后估计。

### v0.1 必过场景

1. 新建一个学习会话，模型生成真实回答，在两处文字建立不同批注。
2. 在一个批注中继续两轮，再从其中一个回答创建子批注。
3. 主线消息数量和顺序不因旁支追问改变；另一个旁支的专属信息不泄漏到当前旁支上下文。
4. 从树和高亮打开记录、返回源位置；退出和重启后保持一致。
5. 生成失败、取消、令牌失效时有清晰状态；部分内容可恢复，重试不会重复创建记录。
6. Markdown 导出可阅读；完整备份导入后恢复会话、版本、批注和关系。
7. 重生成保留旧版本引用；重复文本、emoji 和公式显示不让批注跳到错误位置。
8. 安装版可以关闭批注面板，也可以关闭批注功能；普通聊天仍能使用。
9. 从父批注进入子批注后返回，主线与父批注各自的阅读位置保持；历史列表选中会话后按最终确定的交互收回。
10. 使用固定长会话数据集测量追问树首次打开、再次切换与滚动响应。P1 记录目标设备和预算，P4 对照验收，不能仅凭框架选择宣称性能良好。

## 9. 功能想法如何进入大纲

统一记录在 [FEATURES.md](FEATURES.md)，给每项稳定编号，避免零散想法只留在聊天里。

每个想法记录：使用场景 → 期望行为 → 优先级 → 依赖 → 验收条件。用户尚未确认的扩展功能标为候选。

技术路线、商业形式或同步机制改变时，更新这里的决策和阶段范围；不要让早期建议变成隐含的固定约束。

## 10. 官网、下载与用户数据

**初期无需自行购买或运维一台服务器。官网、安装包分发、用户同步数据分别安排。**

| 需求 | 建议初期方案 | 何时扩展 |
| --- | --- | --- |
| 官网展示、截图、使用说明 | 静态网站托管，域名可另买 | 有可展示的产品或内测包时上线 |
| 安装包下载 | 发布托管或对象存储，官网链接到具体版本 | 文件体积、访问量与更新需求增长时调整 |
| 聊天、批注和笔记 | 本机 SQLite 与用户备份 | 需要跨设备同步时增加服务端 |
| API Key / ChatGPT 授权令牌 | 当前设备的安全存储 | 不随普通笔记同步或进入下载站点 |
| 多设备账号与同步 | 暂缓；托管认证、数据库和对象存储是候选 | 定义同步范围、离线冲突与权限后实施 |
| 产品统一付费调用模型 | 若后续采用，增加服务端网关、用量与计费 | 服务商产品凭据需要留在服务端 |

静态托管仍由服务商提供服务器资源，只是无需自己管理机器。Cloudflare 官方目前建议新项目采用 Workers，也支持直接托管静态资源；这是一类候选方案，最终根据目标用户访问体验和费用选择。[Workers 静态资源](https://developers.cloudflare.com/workers/static-assets/)

较大安装包适合独立的发布下载服务或对象存储。官网资源与安装包分开，避免超过静态平台单文件限制。例如 Pages 当前单文件限制为 25 MiB，大文件需要其他存储方案。[Pages 限制](https://developers.cloudflare.com/pages/platform/limits/)、[R2 对象存储](https://developers.cloudflare.com/r2/)

未来用户同步可评估托管后台，例如 Supabase 提供 Postgres 数据库和认证。托管服务降低机器运维工作，但仍需自己实现同步协议、用户隔离、冲突处理、备份与账号删除。[数据库](https://supabase.com/docs/guides/database/overview)、[认证](https://supabase.com/docs/guides/auth)

官网不应该直接提供用户的私有数据库下载。初版离线可阅读已保存内容，AI 生成依赖所选模型服务的网络连接。

推进顺序：本地初版 → 展示与下载官网 → 按需求增加账号和同步 → 有规模或特殊控制要求时再评估自管服务器。

## 11. setup.exe 与安装文件夹

setup.exe 通常是安装程序，不是编程语言。它把应用主程序、依赖库、界面资源和卸载组件等复制到安装目录；运行后还会有独立的用户数据目录。

不同框架都可能产出 exe，单靠安装包和文件数量无法确定朋友的软件使用哪种语言。Electron、Tauri、Flutter 和 .NET 等都有自己的打包方式；需要更多明确线索才能判断。

ChatNote 也可以提供 Windows 安装包。开发时使用多种语言，并不要求用户安装开发工具；运行时依赖如何随包提供或由安装程序处理，需要在交付阶段验证。
